## Goal
A 3-node kind cluster on the laptop that behaves like a small real cluster: browser traffic on ports 80/443 reaches a Gateway API controller (Traefik), `kubectl top` and the HPA have metrics, and the four PayFlow images are available on every node. Everything in Phase 3 runs on this.

## What I did
1. **Cluster config** — `kind/cluster.yaml` (kind v0.33.0): 1 control-plane + 2 workers, every node pinned to `kindest/node:v1.37.0@sha256:…` (image and digest from the kind release notes). The control-plane gets the `ingress-ready=true` label and maps host ports 80 and 443, bound to `127.0.0.1` only, so the cluster is not reachable from the rest of the network. Checked first that nothing on the host used 80/443:
   ```bash
   sudo ss -ltnp | grep -E ':(80|443)\s'   # printed nothing
   ```
2. **Create the cluster** — the name comes from the config file, so no `--name` needed.
   ```bash
   kind create cluster --config kind/cluster.yaml
   kubectl config current-context   # kind-payflow
   kubectl get nodes -o wide
   ```
3. **Gateway API CRDs + Traefik** (instead of ingress-nginx, see Problems). CRDs pinned to the version Traefik v3.7 supports, applied server-side because the manifests are too large for client-side apply:
   ```bash
   kubectl apply --server-side -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.3/standard-install.yaml
   helm repo add traefik https://traefik.github.io/charts
   helm upgrade --install traefik traefik/traefik \
     -n traefik --create-namespace \
     -f kind/traefik-values.yaml --version 42.3.1 --skip-crds
   ```
   `kind/traefik-values.yaml`: Gateway provider on; Ingress and IngressRoute (CRD) providers and the IngressClass off; chart's default Gateway off (PayFlow writes its own in 3.4); `hostPort` 80/443 on the `web`/`websecure` entrypoints; Service `ClusterIP`; `nodeSelector ingress-ready: "true"` + toleration for the control-plane taint; `maxSurge: 0, maxUnavailable: 1`.
4. **metrics-server** — chart 3.14.0 (app 0.9.0), one extra arg in `kind/metrics-server-values.yaml`:
   ```bash
   helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
   helm upgrade --install metrics-server metrics-server/metrics-server \
     -n kube-system -f kind/metrics-server-values.yaml --version 3.14.0
   ```
   `args: [--kubelet-insecure-tls]` — appended after the chart's `defaultArgs`.
5. **Load the images** — rebuilt from `payflow-app` main, retagged with the names CI will push in Phase 5, and copied into all 3 nodes:
   ```bash
   docker compose build
   for svc in frontend accounts-api payments-api notification-worker; do
     docker tag "payflow/${svc}:dev" "ghcr.io/owais-io/payflow-${svc}:0.1.0"
     kind load docker-image "ghcr.io/owais-io/payflow-${svc}:0.1.0" --name payflow
   done
   ```
6. Three PRs, one per config file: `kind/cluster.yaml` (#19), `kind/traefik-values.yaml` (#20), `kind/metrics-server-values.yaml` (#21).

## Problems and fixes
| Problem (error message) | Cause | Fix |
|---|---|---|
| Plan said ingress-nginx | ingress-nginx was retired in March 2026: no more releases or security fixes | Switched to Traefik as a Gateway API controller (routes via `Gateway` + `HTTPRoute`, not `Ingress`); updated 3.1.3, 3.4.1 and later items in the checklist |
| First installed Gateway API CRDs v1.7.0 | Took the newest release; Traefik v3.7 supports v1.6.3. CRDs newer than the controller supports have broken Traefik before | `kubectl delete -f` the v1.7.0 manifest (also removes its `safe-upgrades` admission policy, which would block an in-place downgrade), then applied v1.6.3. Nothing used the CRDs yet, so this was safe |
| Traefik's install NOTES suggest Gateway API v1.6.1 | Chart notes lag behind the provider docs | Followed the v3.7 provider docs (v1.6.3); the cluster works with it |
| `helm show values … \| grep "providers.kubernetesGateway.enabled"` found nothing | Values are nested YAML; the dotted path only appears in comments | Saved defaults to a file and read them; `grep -n -A15 '^providers:'` or `yq '.providers.kubernetesGateway'` |
| `service.type` would fail the install | The chart's schema only allows `service.spec.type` (`additionalProperties: false`) | Used `service.spec.type: ClusterIP` |
| `gh create pr --fill` → unknown command | Typo: subcommand order is `gh pr create` | `gh pr create --fill` |
| `gh pr create` asked where to push | Branch not pushed yet | `git push -u origin <branch>` first, then `gh pr create --fill` |
| `kind/.gitkeep` deletion left unstaged after the first commit | `git add kind/` ran before `rm kind/.gitkeep` | Staged the deletion and committed it on the same branch before the PR |
| metrics-server pod `0/1` right after install | Normal: it needs one scrape cycle before readiness passes | Waited ~30 s, became `1/1` |

## What I learned
- **kind nodes are containers.** `extraPortMappings` are Docker port mappings on the node container; `listenAddress: 127.0.0.1` keeps them on localhost. The nodes have their own containerd, so they can't see my Docker images: `kind load docker-image` copies them in.
- **Gateway API is a spec, Traefik is a controller.** The CRDs define `GatewayClass`, `Gateway`, `HTTPRoute`; Traefik watches them and does the routing. The Traefik chart creates the `traefik` GatewayClass; `ACCEPTED True` means Traefik has claimed it.
- **Versions come in linked pairs.** Gateway API CRDs v1.6.3 ↔ Traefik chart 42.3.1 (v3.7.17). Before upgrading the chart, check the new version's provider docs and move the CRDs with it. `--skip-crds` keeps the chart from installing its own CRD versions.
- **hostPort on one node has side effects.** The control-plane is tainted `NoSchedule` in a multi-node kind cluster, so Traefik needs a toleration. Only one pod can hold hostPort 80 on that node, so the default rolling update (surge a new pod first) would hang Pending: `maxSurge: 0, maxUnavailable: 1` replaces it instead.
- **Entrypoint ports vs host ports.** Traefik runs as non-root and listens on 8000/8443 inside the container; hostPort maps 80/443 onto them. Gateway listeners must use 8000/8443.
- **`--kubelet-insecure-tls` is kind-only.** kind's kubelets serve self-signed certificates without the node IPs, so metrics-server can't verify them. EKS kubelets have valid certificates: the EKS overlay (Phase 10) must not carry this flag.
- **Why not `:latest`.** For `:latest`, Kubernetes defaults `imagePullPolicy` to `Always`, so the node would try GHCR (empty until Phase 5) and fail with `ErrImagePull`. A fixed tag like `0.1.0` defaults to `IfNotPresent` and uses the loaded image.
- **Use the final image names now** (`ghcr.io/owais-io/payflow-<service>`), so the manifests in 3.3 don't change when CI starts pushing.

## Interview angle
**Q: Why Gateway API instead of Ingress for a new cluster?**
A: Ingress only covers basic host/path routing, and everything else lives in controller-specific annotations, so configs aren't portable. Gateway API makes those features part of the spec, splits responsibilities into `GatewayClass` (infra), `Gateway` (platform team) and `HTTPRoute` (app team), and is the direction the Kubernetes project recommends — especially after ingress-nginx, the most common Ingress controller, was retired in March 2026. Because the routes are standard resources, I could swap Traefik for another conformant controller by changing the GatewayClass.
