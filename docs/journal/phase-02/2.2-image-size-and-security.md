## Goal
Measure the images from 2.1 instead of assuming they are good: how big they are and why, which
known vulnerabilities they carry, and whether the Dockerfiles follow best practice. Fix what can
be fixed now, and record the rest with a reason, so CI in 2.3 starts from a known state.

## What I did
1. **Measured image size three ways (2.2.1).** Built accounts-api as a naive single-stage image on
   the full `python` base, as a single-stage image on the slim base, and as the real multi-stage
   image, using two throwaway Dockerfiles in `/tmp`:
   ```bash
   docker build -t accounts-api:naive       -f /tmp/Dockerfile.naive       services/accounts-api
   docker build -t accounts-api:single-slim -f /tmp/Dockerfile.single-slim services/accounts-api
   docker images accounts-api
   docker history accounts-api:<tag>
   ```
   Recorded the results in the README ("Image sizes"), then removed the throwaway images and files.
2. **Installed Trivy 0.76.1 and verified it (2.2.2).** Trivy's release pipeline was compromised in
   March 2026 (v0.69.4, and Docker Hub images v0.69.5/0.69.6, were malicious), so I installed a
   specific version and checked its signature with cosign before installing:
   ```bash
   cosign verify-blob trivy_0.76.1_Linux-64bit.deb \
     --bundle trivy_0.76.1_Linux-64bit.deb.sigstore.json \
     --certificate-identity-regexp '^https://github\.com/aquasecurity/' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com
   sudo apt install ./trivy_0.76.1_Linux-64bit.deb
   ```
3. **Scanned all four images:**
   ```bash
   for i in accounts-api payments-api notification-worker frontend; do
     trivy image --severity HIGH,CRITICAL $i:dev
   done
   ```
4. **Scanned the newer base images before switching to them.** `python:3.12.16-slim-trixie` now
   points to a newer digest (`5e2bdb1b…`, built 2026-11-05) than my pin (`4840d514…`), but it has
   the same 49 findings, so switching would change nothing. The `nginx-unprivileged:1.30.6-alpine`
   digest had not changed at all (it is rebuilt weekly).
5. **Frontend: upgraded its Alpine packages in the Dockerfile.** All 10 findings had fixes in the
   Alpine 3.24 repository, including one CRITICAL, so I added a temporary, commented step:
   ```dockerfile
   # TEMPORARY (2026-11-08): the pinned base still has Alpine packages with
   # published fixes (brotli CRITICAL; curl, expat, musl, zlib HIGH).
   # Remove this block once a Trivy scan of the pinned base shows them fixed.
   USER 0:0
   RUN apk upgrade --no-cache
   ```
   The existing `USER 101:101` later in the file switches back to the nginx user.
6. **Python images: left as they are.** Only 2 of the 49 findings have a fix (zlib1g), and only
   through a rebuilt base image. Recorded with a reachability note instead of adding apt layers.
7. **Installed hadolint 2.15.1 and linted the Dockerfiles (2.2.3).** Checked the download against
   its `.sha256` file (hadolint publishes checksums but no signatures). One finding, fixed:
   ```text
   frontend/Dockerfile:9 DL3066 info: Non-numeric user-id may not be resolvable by host system
   ```
   `USER root` → `USER 0:0`, matching the numeric `USER` lines everywhere else.
8. **Added hadolint to pre-commit**, frozen to a commit SHA instead of a tag:
   ```bash
   pre-commit autoupdate --freeze --repo https://github.com/hadolint/hadolint
   ```
   ```yaml
   - repo: https://github.com/hadolint/hadolint
     rev: 2eece55955ced00200be9729e9728cb7dacca505  # frozen: v2.15.1
   ```
9. **Commit (2.2.4).** Merged as payflow-app PR # 10.

## Problems and fixes
| Problem | Cause | Fix |
|---|---|---|
| Multi-stage image 4 MB *bigger* than single-stage | `python -m venv` puts its own pip into `/opt/venv`, which ships | Kept multi-stage for what it keeps out (build files, root-owned venv); documented the result |
| Tag `3.12.16-slim-trixie` resolved to `5e2bdb1b…`, not my pinned `4840d514…` | The tag was re-pushed: a moving tag | The digest pin kept my builds on the tested image; scanned the new digest before deciding |
| 1 CRITICAL + 9 HIGH with fixes in the frontend | The pinned nginx base ships older Alpine packages | Temporary `apk upgrade --no-cache` step, with a removal condition in the comment |
| `DL3066 Non-numeric user-id` | `USER root` in the new block | `USER 0:0` |
| Trivy lists CVE-2026-76844 against zlib with a "webpack-dev-middleware" title | Looks like bad data in the vulnerability database | Checked the entry instead of acting on the title |

## What I learned
- **Measure before claiming.** Almost all of the size saving (84% smaller download) came from the
  slim base; multi-stage added 3 MB here because every dependency is a pre-built wheel. It pays off
  when something has to be compiled, so the builder stage keeps compilers out of the runtime.
- **A scanner count is not a risk score.** 36 of the 49 HIGH findings are util-linux bugs in
  `mount`/`nsenter`, which need privileges a UID 10001 process does not have. Status matters as much
  as severity: only findings with a fix are actionable.
- **Fix OS packages at the base image.** Bumping the pinned digest is the clean way; an in-Dockerfile
  package upgrade is a dated, temporary exception for a fixable CRITICAL.
- **Check a new base before switching.** The newer Python digest looked like an update but fixed
  nothing.
- **Pin your tools like your images.** Trivy was installed by exact version and verified with a
  signature; the hadolint pre-commit hook is pinned to a commit SHA, because a tag can be moved.
  A checksum (hadolint) proves the download was not corrupted, not who published it.

## Carried forward
- **Remove the frontend's `apk upgrade` block** once a Trivy scan of the pinned nginx base shows the
  10 findings fixed (after the weekly rebuild).
- **Bump the Python base digest** once a rebuilt `3.12.16-slim-trixie` contains the fixed zlib1g;
  scan it first. The zlib bug (`gz_vacate()`) is in the `gzFile` API, which the services most likely
  do not use. Not verified against the zlib source.
- **2.3 CI gate:** `--ignore-unfixed` will *not* hide the 2 zlib1g findings, because their status is
  `fixed` (the fix is in Debian but not in the base image). Decide the gate's policy with that in mind.
- **Freeze the other pre-commit hooks** (`pre-commit-hooks`, `ruff-pre-commit`) to SHAs too.
- **Upgrade Trivy to 0.76.2** (it was released during this task), with the same verify-then-install steps.

## Interview angle
**Q: Your scanner reports 49 HIGH vulnerabilities in an image. What do you do?**
A: Split them by status first. Here only 2 of 49 had a fix, and those were in the base OS, so the
fix is a rebuilt base image, not a code change. For the rest, check reachability: most were in
`mount`/`nsenter`, which a non-root container cannot use. Fix what is fixable at the base, take a
dated, documented exception for a fixable CRITICAL (as I did for the frontend), record the rest
with a reason, and let CI enforce the policy from then on.
