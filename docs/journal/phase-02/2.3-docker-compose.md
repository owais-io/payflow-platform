## Goal
Run the whole PayFlow stack (four services, PostgreSQL, Redis) with one command, started in the
right order, configured from a gitignored `.env`, and with database data that survives a restart.
This replaces six terminals of `docker run` and uvicorn, and is the model the Kubernetes manifests
in Phase 3 will follow.

## What I did
1. **Wrote `compose.yaml` with six services (2.3.1).** The four app services build from their own
   Dockerfiles (`build: services/accounts-api`, `image: payflow/accounts-api:dev`); PostgreSQL and
   Redis use `postgres:17` and `redis:7`. Inside the compose network, services reach each other
   by service name (`postgres:5432`, `redis:6379`, `accounts-api:8001`), not `localhost`.
2. **Ordered the start-up with `depends_on` conditions.** A plain `depends_on` only waits for a
   container to *start*; `condition: service_healthy` waits for its healthcheck to pass.
   ```text
   postgres, redis ──► accounts-api ──► payments-api ──► frontend
                       redis ──► notification-worker
   ```
   - payments-api waits for accounts-api too: it calls it, and both run `create_all` on startup,
     so ordering them avoids two processes creating tables at the same time.
   - frontend waits for both APIs, because nginx fails at startup if it can't resolve an upstream.
3. **Healthchecks.** Added `pg_isready` and `redis-cli ping` checks. The app images already have a
   `HEALTHCHECK`, but with `--interval=30s` the first check only runs after ~30 s, so the chain would
   take ~90 s. In compose I added `start_period: 20s` and `start_interval: 2s` (fast checks only
   while starting). For the two APIs I also changed the check from `/healthz` to `/readyz`, so
   "healthy" means "can reach the database", which is what dependants need.
4. **Routed `/api` without changing the frontend image.** The image's nginx config serves static
   files only (routing is the Ingress's job in Kubernetes). Added `frontend/dev/nginx.compose.conf`
   (proxies `/api/accounts` and `/api/payments` to the services by name, keeps `/healthz`) and mounted
   it read-only over `/etc/nginx/conf.d/default.conf`.
5. **Published only the frontend port.** PostgreSQL and Redis stay inside the network, so they
   don't clash with my older `payflow-pg` / `payflow-redis` containers on 5432 / 6379.
6. **Moved config into `.env` (2.3.2).** Used compose *interpolation* (`${VAR}` in compose.yaml,
   filled from `.env`) rather than `env_file:`, so each service receives only the variables listed
   for it. Secrets are required (`${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}`), optional
   settings have defaults (`${LOG_LEVEL:-INFO}`, `${FRONTEND_PORT:-8081}`). `DATABASE_URL` is built
   from the same three `POSTGRES_*` variables the database uses, so they can't drift apart. In the
   healthcheck I used `$${POSTGRES_USER}`: `$$` escapes compose interpolation, so the shell inside
   the container reads its own variable. Documented everything in `.env.example`.
   ```bash
   cp .env.example .env
   git check-ignore -v .env        # .gitignore:153:.env   .env
   docker compose config | grep -e DATABASE_URL -e published
   ```
7. **Gave PostgreSQL a named volume (2.3.3)** mounted at `/var/lib/postgresql/data` (the data path
   for `postgres:17`; it changes to `/var/lib/postgresql` in 18). Redis has no volume on purpose: it
   only carries events in flight.
   ```yaml
   volumes:
     - pgdata:/var/lib/postgresql/data
   # top level
   volumes:
     pgdata:
   ```
8. **Updated the README** with a "Run it with Docker Compose" section and new Troubleshooting rows;
   the manual run is kept as "without Docker Compose" (2.3.4).

## How I verified it
Whole stack up, in order, in about 12 s:
```text
✔ Container payflow-app-postgres-1            Healthy    7.2s
✔ Container payflow-app-redis-1               Healthy    7.2s
✔ Container payflow-app-notification-worker-1 Started    6.3s
✔ Container payflow-app-accounts-api-1        Healthy   10.3s
✔ Container payflow-app-payments-api-1        Healthy   12.2s
✔ Container payflow-app-frontend-1            Started   12.3s
payflow-app-frontend-1   ...  Up (healthy)   0.0.0.0:8081->8080/tcp
```
A transfer from the browser reached the worker:
```text
{"service": "notification-worker", "message": "notification sent", "amount": "500.00", "currency": "PKR", ...}
```
`.env` fills in the config, and a missing one fails clearly:
```text
DATABASE_URL: postgresql+psycopg://payflow:<password>@postgres:5432/payflow
published: "8081"
error while interpolating ...: required variable POSTGRES_USER is missing a value: set POSTGRES_USER in .env
```
Data survives `down` / `up` with the volume, and `down -v` removes it:
```bash
docker volume ls | grep pgdata          # local  payflow-app_pgdata
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from accounts;"'
#  count = 2  →  docker compose down && docker compose up -d  →  count = 2
docker compose down -v                  # ✔ Volume payflow-app_pgdata  Removed
```
Before the volume, the browser showed every earlier account as "not found" after a `down` / `up`
(screenshot: `docs/img/2.3-no-volume-not-found.png`).

## Problems and fixes
| Problem (error message) | Cause | Fix |
|---|---|---|
| `failed to bind host port 0.0.0.0:8080/tcp: address already in use` | Something on the host already uses 8080 | Host port `${FRONTEND_PORT:-8081}`; 8080 stays free for Jenkins (Phase 7) |

## What I learned
- `depends_on` alone is only about start order; `condition: service_healthy` is what makes a
  service wait until its dependency can actually serve. Which endpoint the healthcheck calls
  decides what "healthy" means: liveness (`/healthz`) or readiness (`/readyz`).
- A compose healthcheck that sets only timings keeps the image's `test`. `start_interval` makes
  start-up fast without making steady-state checks noisy.
- Compose interpolation (`${VAR}` from `.env`) and `env_file:` are different: interpolation lets me
  choose exactly which variables each container gets. `:?` makes a variable required, `:-` gives a
  default, `$$` passes a literal `$` to the container.
- A bind mount whose source is missing silently becomes a root-owned directory. Named volumes are
  for data Docker owns (the database); bind mounts are for files I edit (the nginx config).
- `docker compose down` keeps volumes; `down -v` deletes them. `POSTGRES_*` variables are only read
  when the volume is empty, so changing the password later needs `down -v` or `ALTER USER`.

## Interview angle
**Q:** What's the difference between `depends_on` and `condition: service_healthy`, and why did
you check `/readyz` instead of `/healthz`?
**A:** `depends_on` only waits for the container to start; with `service_healthy` compose waits
until the healthcheck passes. `/healthz` only proves the process is up; `/readyz` proves it can
reach PostgreSQL, so a service that depends on it won't start against an API that can't serve yet.
In Kubernetes the same split becomes liveness vs readiness probes.

## Tutorial notes (for beginners)
- Prerequisites: Docker with Compose v2 (`docker compose version`), the images from 2.1 building.
- Common mistake to warn about: running `up` before the mounted file exists. Docker creates a
  root-owned directory in its place, and the error message talks about directories, not a
  missing file.
