## Goal
One command that answers "does the running stack actually work?" with an exit code a machine can
act on. CI will run it after a deploy (Phase 5) and Jenkins before promoting to prod (Phase 7), so
it has to be non-interactive, readable in a log, and able to tell "broken" from "not there".

## What I did
1. **Wrote `scripts/smoke_test.py` (2.4.1).** Standard library only, like `seed.py`, so it runs
   anywhere without a virtualenv. Design decisions:
   - **Goes through the gateway** (`--base-url`, default `$SMOKE_BASE_URL` or
     `http://localhost:8081`) and calls `/api/accounts` and `/api/payments`, so it tests the path a
     browser takes, nginx routing included. Later the same script points at the Ingress.
   - **Waits before testing** (`--wait 60`): retries until the API answers through the gateway.
     Any HTTP answer counts as up (even a 404 for a made-up ID); 502/503/504 means the gateway is up
     but the API behind it is not yet. Right after a deploy, "still starting" is not a failure.
   - **Unique account names per run** (`smoke-<timestamp>-A`), because PostgreSQL keeps data now.
   - **Money as `Decimal`**, never `float`.
   - **No `assert`** (removed under `python -O`): a `check(name, ok, detail)` helper prints
     PASS/FAIL and counts.
   - **Exit codes:** `0` all passed · `1` a check failed, including part of the stack not answering
     mid-test · `2` the stack could not be reached before testing started (nothing was tested).
2. **Five checks:**

   | # | Step | Expect |
   |---|---|---|
   | 1 | Create A with 1000.00, B with 0.00 | balances echoed back |
   | 2 | Transfer 250.00 A → B | 201, `status: completed`, amount 250.00 |
   | 3 | Read both balances from accounts-api | A = 750.00, B = 250.00 |
   | 4 | `GET /api/payments?account_id=A` | the payment from step 2 is listed |
   | 5 | Transfer 10000.00 A → B (overdraft) | **409**, and both balances unchanged |

   Check 5 makes this a payments test, not a ping: it proves the insufficient-funds rule and the
   rollback in the running system.
3. **Made it fail on purpose** (`docker compose stop payments-api`). That exposed two problems,
   one in my script and one in nginx (see Problems and fixes); both fixed.
4. **Fixed nginx in compose (`fix/nginx-compose-resolver`).** `nginx.compose.conf` now resolves
   service names at request time through Docker's DNS:
   ```nginx
   resolver 127.0.0.11 valid=10s ipv6=off;
   resolver_timeout 2s;
   proxy_connect_timeout 2s;

   location /api/payments {
       set $payments_api http://payments-api:8002;   # a variable makes nginx re-resolve
       rewrite ^/api(/.*)$ $1 break;
       proxy_pass $payments_api;
   }
   ```
5. **Ran it against a clean stack from `main` (2.4.2)** with freshly built images:
   ```bash
   docker compose down && docker compose up -d --build && python3 scripts/smoke_test.py
   ```
6. **Checked Phase 2's other exit criterion:** no CRITICAL findings in any image.
   ```bash
   for i in accounts-api payments-api notification-worker frontend; do
     trivy image --quiet --severity CRITICAL payflow/$i:dev
   done
   ```

Merged as payflow-app PR #12 (smoke test) and #13 (nginx fix); the README section on the
smoke test followed in a small docs PR.

## Interview angle
**Q: Your smoke test fails in the pipeline. How does the pipeline know whether to roll back?**
A: By the exit code. Exit 2 means the stack never answered, so the deploy isn't ready yet:
retry or wait. Exit 1 means it answered but behaved wrongly (a failed check, or a service
stopped answering mid-test): that's a bad release, so roll back. I tested both by stopping a
service on purpose, which is how I found that nginx was caching a dead container's IP.
