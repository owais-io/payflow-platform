## Goal
Build the first real service: accounts-api, with the three endpoints from the design doc,
stored in PostgreSQL, and with the operational basics every PayFlow service needs: health and
readiness probes, Prometheus metrics, JSON logs and unit tests with a coverage gate.

## What I did
1. Scaffolded the project with `pyproject.toml`, a virtualenv and an editable install.
   ```bash
   cd services/accounts-api
   python3 -m venv .venv && source .venv/bin/activate
   pip install -e ".[dev]"
   ```
2. Added `POST /accounts`, `GET /accounts/{id}`, `GET /accounts/{id}/balance` with Pydantic
   validation, first against an in-memory store behind a `get_store()` dependency.
3. Ran PostgreSQL in Docker and swapped in a SQLAlchemy store; all config from env vars.
   ```bash
   docker run -d --name payflow-pg -e POSTGRES_USER=payflow -e POSTGRES_PASSWORD=payflow \
     -e POSTGRES_DB=payflow -p 5432:5432 postgres:17
   set -a; source .env; set +a
   uvicorn app.main:app --reload --port 8001 --no-access-log
   ```
4. Added `/healthz` (liveness, no dependencies) and `/readyz` (`SELECT 1` against PostgreSQL).
5. Added `/metrics`: a middleware counts and times every request, labelled by route template.
6. Switched all logs, uvicorn's included, to one JSON object per line on stdout.
7. Wrote 23 pytest tests that run without a database; coverage gate at 70%.
   ```bash
   env -u DATABASE_URL pytest
   ```
8. Squash-merged the branch through a PR.

## Interview angle
**Q:** What's the difference between a liveness and a readiness probe, and what should each one check?
**A:** Liveness asks whether the process is alive; if it fails, Kubernetes restarts the pod, so it should check
nothing external. Readiness asks whether the pod can serve traffic right now; if it fails, the pod is removed
from the Service until it passes, so it checks dependencies like the database. Putting a DB check in liveness
turns a database outage into a restart storm across every pod.
