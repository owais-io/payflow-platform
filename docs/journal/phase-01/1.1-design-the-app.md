## Goal
Write down how PayFlow works before writing any code: what each service does, the API
contracts, the database tables and the event between services. Every later phase builds
on this map. The code, the Kubernetes manifests, the NetworkPolicies and the alerts all follow from it.

## What I learned
- **Shared database, one owner per table.** accounts-api owns `accounts`; payments-api owns `transactions` and updates balances only inside a transfer. A transfer is one DB transaction, so it is never half-done. The trade-off is that pure microservices don't share a database, which I accepted to keep the code simple.
- **UUIDs instead of 1, 2, 3.** Sequential IDs let anyone guess other customers' account numbers.
- **Money is never a float.** The database stores `NUMERIC(12,2)`; the API sends strings like `"250.00"`. Floats can't represent 0.10 exactly, so rounding errors creep in.
- **Let the database enforce rules too.** `CHECK (balance >= 0)`, `CHECK (amount > 0)`, `from ≠ to` and foreign keys catch bugs the API misses.
- **Lock rows in a fixed order.** If A pays B while B pays A, locking by UUID order prevents a deadlock.
- **409 for insufficient funds.** The request is valid but conflicts with the account's current state; 422 is already FastAPI's "invalid body".
- **Redis Stream over a list.** A list loses the message if the worker crashes mid-way; a stream keeps it pending until `XACK`, and a consumer group shares the work between replicas. Delivery is at least once, so duplicates are possible; for a log line that's fine.
- **The outbox pattern is a known gap.** The DB commit and the Redis publish are two systems, so no single transaction covers both. If Redis is down, the payment succeeds but the event is lost. The fix would be an outbox table, which is out of scope.
- **The design doc feeds DevOps work.** The call map drives NetworkPolicies, the tables drive the migration Job, `/readyz` checks the DB, and the metrics drive alerts.

## Interview angle
**Q:** Your payment is saved to the database, but publishing the event to Redis fails. What happens?
**A:** The payment still succeeds. The event is published only after the commit, so a rolled-back
payment never sends one. If Redis is down, payments-api logs the error and increments a failure metric,
but that notification is lost. The proper fix is the transactional outbox: write the event to a table in
the same DB transaction and have a separate process relay it to Redis. I documented it as a known
limitation instead of building it.
