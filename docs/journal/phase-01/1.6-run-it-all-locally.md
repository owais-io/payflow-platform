## Goal
Prove the whole application works together on one machine before any containers or
Kubernetes: data stores in Docker, every service started by hand, demo data loaded by a
script, and a README that lets someone else do the same from scratch.

## What I did
1. PostgreSQL and Redis with plain `docker run` (containers already existed from 1.2 and 1.3,
   so `docker start`):
   ```bash
   docker start payflow-pg payflow-redis
   ```
2. Installed and started every service from the new README, one terminal each:
   ```bash
   cd services/<service>
   python3 -m venv .venv && source .venv/bin/activate
   pip install -e '.[dev]'
   cp --update=none .env.example .env
   set -a && source .env && set +a
   uvicorn app.main:app --port 8001 --no-access-log   # accounts-api
   uvicorn app.main:app --port 8002 --no-access-log   # payments-api
   python -m app.main                                 # notification-worker
   ```
   Frontend on 8081 (8080 is taken by a host Jenkins), using a temporary copy of the dev config:
   ```bash
   PORT=8081
   sed "s/listen 8080;/listen $PORT;/" dev/nginx.local.conf > /tmp/payflow-nginx.conf
   docker run --rm --name payflow-frontend --network host \
     -v "$PWD":/usr/share/nginx/html:ro \
     -v /tmp/payflow-nginx.conf:/etc/nginx/conf.d/default.conf:ro \
     nginxinc/nginx-unprivileged:1.27-alpine
   ```
3. Wrote `scripts/seed.py`: creates 5 demo accounts and 5 transfers through the APIs, then reads
   the balances back. Standard library only (no virtualenv), works straight against the APIs or
   through a gateway (`--gateway`, nginx now, the Ingress later). Exits 1 with a clear message
   if an API is down.
4. Rewrote the README: services and ports, how to run everything locally, demo data, a curl
   example, tests, and a troubleshooting table built from the problems I hit in Phase 1.
5. Ran every service's unit tests and linters.

Merged as payflow-app PR #8.

## Problems and fixes
| Problem (error message) | Cause | Fix |
|---|---|---|
| `Conflict. The container name "/payflow-pg" is already in use` | The README's first-time `docker run` commands; the containers already existed from 1.2/1.3 | `docker start payflow-pg payflow-redis` (the README shows both cases) |
| payments-api: `error while attempting to bind on address ('127.0.0.1', 8001): address already in use` | Pasted accounts-api's command with `--port 8001` | Restarted with `--port 8002` |
| `ModuleNotFoundError: No module named 'uvicorn'` in the worker terminal | Ran the uvicorn command for the worker, which is not a web app and has no uvicorn | `python -m app.main` |
| First `curl localhost:8002/readyz` returned nothing | payments-api had not started yet (it had failed on port 8001) | Checked again after starting it on 8002 |
| nginx: port 8080 in use | A host Jenkins (`java`) listens on 8080 | Used 8081 via a `sed` copy of the config; added this to the README so others can do the same |

## What I learned
- **Starting the stack by hand shows every dependency:** PostgreSQL and Redis first, then accounts-api
  (payments-api calls it), then payments-api, then the worker and the frontend. This order is
  exactly what Kubernetes probes and ArgoCD will have to handle later.
- **A README is tested by following it.** Running my own README from scratch found the
  "container already exists" and port-clash cases, which are now in it.

## Interview angle
**Q: How do you check that a multi-service app actually works end to end, not just each part?**
A: Follow one request through every service by its ID. I make a payment and find the same
`payment_id` in payments-api's "payment completed" log and in the worker's "notification sent"
log, and check the balances that accounts-api returns. Seeding through the public API, not the
database, means the test data goes through the same rules and events as real traffic.
